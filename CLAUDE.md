# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Musiklib: a minimal, fast music library for a personal MP3 collection. Runs as a small Docker container on an unraid NAS, scans a music directory, and serves a single HTML page with search and an integrated player, reachable from any device on the network. No database — everything the app knows lives in `library.json`.

The application the container runs is six files:
- `app.py` — FastAPI backend: scanning, JSON API, streaming.
- `index.html` — the previous desktop frontend, served at `/klassisch` only since stage 4. `/` now serves `player.html`; this one stays one release as the way back. HTML + CSS + vanilla JS in one file, no build step, no framework.
- `mobile.html` — the previous phone frontend, now served at `/mobil-alt` only. Since stage 3 its five appearances live in `player.html` as layouts with target `telefon`, and `/mobil` serves that file; this one stays one release as the way back (see below).
- `player.html` — **the app**, served at `/`, `/mobil`, `/ipad` and `/pc` (one file, four routes), seventeen selectable layouts — twelve for tablet and desk, five ported from `mobile.html` for the phone — plus the shared settings dialog that carries the target, sorting, the artist view, accents and the scan (see below).
- `tag.html` — the album of the day at `/tag`: one button, no choices at all (see below).
- `requirements.txt` — pinned deps: `fastapi`, `starlette`, `mutagen`, `uvicorn`, `uvloop`, `httptools`. `starlette` is pinned explicitly even though it only arrives via FastAPI: it provides the `FileResponse` that implements Range streaming, and versions before 1.3.1 parse Range headers in quadratic time (a single request stalls the event loop for minutes). `uvicorn` is installed without the `[standard]` extra — `uvloop` and `httptools` are listed directly instead, so the unused `websockets`/`watchfiles`/`PyYAML`/`python-dotenv` don't get pulled in.

`conftest.py`, `test_app.py`, `test_frontend.py` and `requirements-dev.txt` exist only for local development — the compose `command` installs `requirements.txt` alone, so none of them ever reaches the container. `docker-compose.yml` and `README.md` (in German) cover unraid deployment; not relevant to app logic.

`mockups/` holds design drafts, never anything the container serves: `handy.html`/`faden.html`/`faden-cover.html` are the drafts `mobile.html` came out of, and five further pages from the same round are the search that led there — `vorbilder.html` (nineteen drafts after outside references), `varianten.html` (five of them × five material treatments), `farben.html` (eight treatments × three colour readings), `glanz.html` (the same eight matte / gloss / mixed) and `kassette.html` (a second take on the cassette, five real types). Each is one self-contained file with live, operable phone mockups and German commentary; they were recovered from the unmerged branch `claude/player-ui-integration-mockups-pzjhw1` and are **candidates, not decisions** — nothing on them is built. That branch also carried **eight further `mobile.html` themes** (Der echte Abzug, Die Entwicklung, Milchglaszeilen, Programmheft, Die Spur, Emaille, Gespritzt, Abreißkalender). Their code is *not* merged into the app — they predate the consolidation, so those appearances belong in `player.html` as layouts now, which makes each of them a port and not a restore. But the branch was their only copy, so `mockups/acht-themen/` now holds that `mobile.html` byte-identical, plus one screenshot per theme and a `LIESMICH.md` explaining what it is, how to run it and what porting one would mean. **That folder is a frozen snapshot, not a second system — never edit it and never copy it over the root `mobile.html`.** `mockups/player/` holds twenty-two sheets (`index.html` is the overview) with thirty-eight player variants, in three groups: sheets 02–14 are the first row, drawn from the photos in `mckups_player/`, and `player.html`'s twelve layouts, `mobile.html`'s three extra themes and `tag.html` were built from them; sheets 15–20 are a second row drawn from named devices instead of photos; sheets **21–25** come from a second photo set, `mckups_player_2/`, one PC and one iPad-quer variant each — 25 Eisblau also has a third, for the phone, because its template is a phone. **Nothing from 15–25 is ported yet.** The last group was drawn on the branch `claude/player-interface-mockups-c64x3u`, never merged, and recovered from there — on that branch it was numbered 14–18, which collides with what main has, so it was renumbered. Anything else still only on that branch is lost work, not history: check it before assuming a sheet is gone. All of them are demos with an invented library and a fake clock — no API, no `localStorage`. `_buendeln.py` (needs Pillow) inlines the sheets, the shared files and the photos from **both** template folders into `alle-blaetter.html`, a single file for passing the whole set around — re-run it after changing any sheet, or the bundle drifts.

## Running locally

There is no linter and no build step. There *is* a pytest suite; run it before and after changes.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt -r requirements-dev.txt
.venv/bin/python -m playwright install chromium   # once, for test_frontend.py
.venv/bin/python -m pytest -q            # rund 147 Tests, ~2.5 min
.venv/bin/python -m pytest -q test_app.py        # backend only, <1 s
.venv/bin/python -m pytest -q -k session         # one group
MUSIC_DIR=/path/to/some/mp3s DATA_DIR=./data .venv/bin/python app.py   # serves on :8080
```

`test_app.py` covers the backend in-process via `TestClient`: Range requests returning 206, cover-endpoint path traversal, the guards that stop a scan from wiping the catalog, cover extraction from a non-first track and from folder images, the tag cache, and the scan lock.

`test_frontend.py` drives all three pages in a real Chromium against `app.py` in a subprocess: for `index.html` search (incl. by track title), sorting, the player and its button/audio synchronisation, volume, shuffle, keyboard shortcuts and session restore; for `mobile.html` — now at `/mobil-alt` — the axis, the settings and the three themes that bring their own player; for the five phone layouts that each builds, plays, stops and stays inside a 390×844 screen, reaches the collection and plays from it, that the collection button does not raise the keyboard while the search button does, that a tap on the rail unfolds the queue without moving playback while a drag seeks across a track boundary, that an accent survives a reload, and that the old `musiklib:einstellungen` is taken over; for `player.html` that every layout builds, plays, stops and reaches its library behind a button, that sorting and the artist grouping reach the list inside a layout, that `musiklib:sort` means the same thing on `/pc` and `/`, that opening the page never starts a scan while the button does, and — since stage 2 — that every layout declares a target, that the chooser filters by it and can be unlocked again, that the choice is remembered per target and an old single-value key is carried over, that every layout offers transport, a marked seek surface and a Wechsler nothing covers, and that volume and mute are reachable from the dialog under the shared keys; for `tag.html` the one-button toggle, the five-tap re-roll and its once-a-day limit, that the daily choice is identical in a second browser context, the endless queue, and that a day change waits for the running track (the last two lean on `heute` and `FENSTER` being reassignable). Without the `playwright` package or a usable browser the whole module skips and the backend tests still run — so a missing browser is never a red suite. `MUSIKLIB_CHROME=/path/to/chrome` overrides browser discovery.

Both files share MP3 fixture builders and the `app_env` fixture from `conftest.py`; the suite needs no audio files of its own. The frontend context blocks `fonts.googleapis.com`, so the tests neither wait on the network nor depend on internet access — keep that when adding pages, or the suite slows down by more than an order of magnitude.

```powershell
$env:MUSIC_DIR = "C:\path\to\some\mp3s"   # defaults to /music
$env:DATA_DIR = ".\data"                   # defaults to /data
python app.py                              # PORT env var to change the port
```

Open `http://localhost:8080`. Startup triggers a scan **only if `library.json` does not exist** — to force a re-scan during development, delete `DATA_DIR` or `POST /api/scan`.

A fresh checkout has no music to scan. `conftest.py`'s `write_mp3()` / `frames()` build fixtures without any audio files on hand: raw MPEG1 Layer III frames (a `\xff\xfb\x90\x00` header + zero padding to 417 bytes, repeated) tagged with `mutagen.id3`; `MP3()` parses these fine and reports a duration. Use the same helpers when scanning a directory by hand.

One trap the frontend tests already ran into: fixture tracks must be **long enough that playback does not run past them** during a test (`TRACK_SECONDS = 30`). With one-second tracks the queue advances between assertions and failures look like real bugs.

`.venv/` and `data/` are gitignored.

## Architecture

**Backend (`app.py`)** does three things:
1. **Scan** (`scan()` → `run_claimed_scan()`) — walks `MUSIC_DIR` recursively for `*.mp3`, reads ID3 tags via `mutagen`, groups tracks into albums (album identity = `stable_id(album_artist, album)`, a truncated SHA1), stores cover art to `DATA_DIR/covers/{album_id}.{jpg|png}`, and atomically writes three files:
   - `DATA_DIR/library.json` — the public, flat album/track structure served to the frontend as-is via `FileResponse`.
   - `DATA_DIR/tracks.json` — an internal `track_id -> absolute filesystem path` map, never exposed to the client; used only by `/api/stream/{track_id}` to resolve playback paths.
   - `DATA_DIR/tagcache.json` — an internal `path -> {mtime_ns, size, tags}` map so the next scan can skip files that have not changed. Guarded by `TAGCACHE_VERSION`: **bump it whenever `read_tags()` changes its output shape**, otherwise stale entries silently survive.
   Scan state (`scan_state` global dict: running/progress/total/skipped/skipped_files/error) is polled by the frontend during a scan and is **not** persisted — it resets on restart.

   `run_claimed_scan()` is deliberately split: `_guard_music_dir()`, `_collect_mp3s()`, `_build_albums()` (the loop, incl. cache lookups), `_finalise_albums()` (track sorting + folder-cover fallback), then writing and `prune_covers()`. Cover art is fetched by `read_cover()` separately from `read_tags()` — that keeps `read_tags()`'s return value JSON-serialisable and therefore cacheable, which is the whole basis of the incremental scan. Don't merge them back.
2. **Serve** — `/`, `/mobil`, `/ipad` and `/pc` all return `player.html` as-is; `/klassisch` returns `index.html` and `/mobil-alt` returns `mobile.html`, both transitional (no UA sniffing anywhere: iPad Safari reports a desktop UA, so the choice is the user's — the two player routes are two names for the same file, not two files); `/api/library` returns `library.json` as-is (no per-request transformation, no pagination — the frontend receives and filters the whole collection client-side).
3. **Stream** — `/api/stream/{track_id}` resolves the id via `tracks.json` and returns a `FileResponse`; Starlette's `FileResponse` handles HTTP Range requests natively, which is what makes seeking work.

Scans are triggered two ways: automatically on startup if `library.json` doesn't exist yet (`lifespan` handler, runs in a background thread via `asyncio.to_thread`), or manually via `POST /api/scan` (also backgrounded, via `BackgroundTasks`). There is deliberately no periodic/automatic re-scan — it's manual only, to avoid waking an idle NAS. Re-running the app never triggers a rescan once `library.json` exists, even if the source files changed.

Because there's no database, `scan()` is the single source of truth for how raw ID3 tags become album/track records — read this function fully before changing library shape or the JSON schema the frontend consumes.

### Consequences of the no-database design

These follow from the code above and are easy to trip over:

- **`track_id` is a hash of the absolute file path.** Moving or renaming an MP3 gives it a new id on the next scan, invalidating anything that stored the old one. Nothing currently persists track ids across scans — keep it that way, or the assumption breaks.
- **`DATA_DIR` is now maintained, not just appended to.** `prune_covers()` deletes cover files no album references any more, and `_write_cover()` compares content before writing, so a swapped cover of an otherwise unchanged album *is* picked up. Deleting `DATA_DIR` is still the way to force a full rebuild, but it is no longer needed for routine cover changes.
- **Rescans are incremental.** Files whose `mtime_ns` and `size` match `tagcache.json` are not re-parsed. That makes repeated scans cheap, and it is why the cache version guard matters: a change to `read_tags()` without a `TAGCACHE_VERSION` bump would leave stale data in the catalog indefinitely.
- **Album cover art has two sources.** Embedded `APIC` first; if no track in the album carries one, `_finalise_albums()` falls back to `cover.jpg`/`folder.jpg`/`front.jpg`/`albumart.*`/`album.*` in the directories that album's files live in.
- **A scan refuses to replace a non-empty catalog with an empty one.** If `MUSIC_DIR` is not a directory, or if it yields zero MP3s while `library.json` still lists albums, `run_claimed_scan()` reports an error in `scan_state["error"]` and writes nothing. Without that guard an unmounted or renamed music share would silently wipe the catalog, because `Path.rglob()` on a missing directory returns an empty iterator instead of raising. Deliberately emptying the library therefore means deleting `DATA_DIR`, not scanning an empty folder.
- **Skipped files are counted and named, not silent.** `read_tags()` still returns `None` on any exception, but the scan counts those files into `scan_state["skipped"]` / `library.json`'s `skipped_count` and records the first `MAX_SKIPPED_REPORTED` names in `skipped_files`, logging one line each. Those names are always relative to `MUSIC_DIR` (`_relative_to_music()`) — `library.json` goes to the browser, so never put an absolute path in it.
- **Album-level fields come from whichever track carries them first**, not from the album's first track. Cover art and `year` are filled in the first time any track of that album supplies them — an intro track without embedded art no longer leaves the whole album coverless.
- **`scan_state` is guarded by `_scan_lock`.** `_claim_scan()` does the check-and-set atomically and `POST /api/scan` claims the slot *before* returning, so a status poll issued immediately after the POST always observes `running: true`. Don't reintroduce a bare flag check.
- **`/api/stream` resolves paths through `_load_tracks()`**, which keeps `tracks.json` parsed in memory and reloads only when its mtime/size change. Don't go back to reading the file per request — every Range request during seeking hits this path.
- **`scan_state["error"]` is a short, user-facing German message**, rendered as-is in the UI. Exception detail goes to the log via `log.exception`, not into the API response.

**Frontend, the previous phone surface (`mobile.html`)** is served at `/mobil-alt` since stage 3 — `/mobil` now serves `player.html`. It stays one release as the way back, and it shares every storage key with the new one, so switching mid-song continues playback. Everything below still describes it, and stays worth reading while its five appearances live on as layouts. It is a *separate, smaller* app against the same API — not a responsive variant of `index.html` and not a shared codebase. What it deliberately leaves out: scanning, the skipped-files list, the sort selector. What it adds: a settings sheet (theme, accent colour, tab-bar behaviour) and the queue-as-axis player.
- Light palette (`--paper` ivory, serif titles, spaced small caps) against `index.html`'s dark one — a phone is held in daylight. Both share the hairline/2px-radius vocabulary.
- **Five themes, and a theme is the whole appearance, not a palette.** `:root` carries "Papier" (ivory/brass, queue as a vertical rail in the right margin); `[data-thema="wueste"]` carries "Desert Rose" (sand/burgundy, queue as a horizontal engraved scale under the cover, cover in a passepartout, centred column, filled play disc). Both come from `mockups/faden-cover.html` (E and F) and share the built-in player.
- **Three further themes bring their own player** (`THEMEN[].spieler`): "Kissen" (`mockups/player/02`), "Karte" (`03`) and "Kiesel" (`05`). What that means concretely:
  - `applySettings()` sets `data-spieler` on `<html>` — **removing the attribute when there is none**, because `[data-spieler]` in CSS also matches an empty value and would keep the built-in player hidden. It then calls `baueSpieler()`, which rebuilds `#fremd` only when the id actually changed.
  - The alternate surface replaces *only* `#view-now`'s `.lid`/`.stage`/`.foot`. Collection, search, album sheet and tab bar are untouched — they just take the theme's colours. **A new theme therefore has to define the whole token set** (`--paper` … `--veil`), not just the player's colours.
  - `renderProgress()` computes the shared state once and hands it to `zeichneSpieler()` *and* to `zeichneRand()`/`zeichneSkala()`; only one of them is visible. `setPlayButton()` also calls `renderProgress()`, because on pause `timeupdate` stops and the alternate player's own button would otherwise keep showing the pause glyph.
  - These three have **no library of their own**: in `mobile.html` the collection and the search are views, so each carries one button to each (`[data-zur-lib]`, `[data-zur-suche]`) in the same place — top left and top right.
  - "Karte" has exactly one accent on purpose: its sheet allows exactly one colour, and that colour carries the playback position.
  - **Every colour must go through a token, including shadows (`--schatten`, an `r,g,b` triple used as `rgba(var(--schatten),.14)`) and the tab bar's veil (`--veil`).** A literal colour anywhere in the stylesheet is a hole through which ivory leaks into the sand.
  - **Both axes live in the DOM**; the theme shows one (`.rail` vs `.skala`) and `skalaAktiv()` is the single place that asks which. `buildRail()` builds *both* tick sets, so switching themes mid-playback doesn't find the other axis empty. `renderProgress()` computes the shared state and hands off to `zeichneRand()` or `zeichneSkala()`.
  - The scale has **no 8px tap/drag threshold** — on a horizontal scrubber a tap is unambiguously a seek, whereas on the rail it unfolds the queue. Both still apply the seek on release only.
  - `layoutQueueList()` returns early under the scale: without a vertical axis, positioning tracks by their time offset orders nothing, so the unfolded queue is a plain centred list there.
- **Accent colours belong to the theme** — `THEMEN[].akzente`, ids unique across all themes (`messing`/`petrol`/`gruen`, `ton`/`rose`, `nebel`/`flieder`, `zinnober`, `graphit`/`stahl`). Brass on sand would not be a choice but a mistake, so switching themes switches the accent with it (`setSettings({thema, akzent})` in one write). Each accent defines two tones: `--accent` carries fills and lines, `--accent-ink` carries text. The green's and the clay's fill tones are deliberately lighter than text contrast would allow — that is why the second tone exists. Adding an accent means one CSS block plus one entry in that theme's array.
- **Settings** are one object in `localStorage` under `musiklib:einstellungen` (`thema`, `akzent`, `leiste`, `fortsetzung`, `wach`), not one key per option, so later options need no new key — `fortsetzung` and `wach` arrived later and needed none. (`fortsetzung` is mirrored from the shared meaning of `musiklib:fortsetzung` in the other two surfaces; the phone keeps it inside its settings object because that is where its control lives.) `applySettings()` is the single place that writes state to the DOM; it validates every value through `gewaehlt()` and falls back to the default, so a hand-edited or outdated key can't leave the UI in a state with no way out. It also updates the `theme-color` meta — otherwise the iPhone paints an ivory strip above the sand.
- **Two bottom-space variables, not one.** `--tabs` is the tab bar's own height and never changes; `--unten` is the space the views and sheets leave free (`inset: 0 0 calc(var(--unten) + var(--safe)) 0`). `[data-leiste="bedarf"]` shrinks only `--unten`, to the 18px plinth that holds the grip — reusing `--tabs` for both would shrink the bar itself.
- **Tab bar on demand** (`einstellungen.leiste`, `dauerhaft` | `bedarf`). In `bedarf` the bar is pushed off-screen with `transform` *and* `visibility:hidden` (transition-delayed), because a merely translated bar keeps three unreachable buttons in the tab order. `zeigeLeiste()` is the only thing that toggles it; it also re-arms the 4s auto-hide. The grip stays visible on purpose — an invisible gesture is not a gesture, and without the bar it is the only way back to another view.
- The bar sits at `z-index:75`, i.e. **above the album sheet (70), below settings (80)**. Permanently it never touches the sheet; summoned over an open album sheet it must be in front of it, not behind.
- **Grid cards carry `min-width:0`** and `align-self:start`. Grid items are otherwise at least as wide as their longest unbreakable content, and the artist line runs `white-space:nowrap` — a long artist name pushed the column past the screen edge and made the collection scroll sideways. Guarded by `test_mobile_grid_never_scrolls_sideways`. The same applies to `.trk .t` in the album sheet.
- **The player is the queue axis** ("der Rand"): a hairline in the right margin with one tick per track. It does not label the tracks — names appear only while dragging (a readout) or when the axis is unfolded via the counter button. That is what removes the density limit a labelled axis would have.
- Tap and drag on that rail are **separate gestures**: seeking starts only after 8px of movement, below that it is a tap that unfolds the queue. Don't merge them back — a tap that also seeks moves playback when the user only wanted to look.
- Seeking across a track boundary goes through `springeZu()`, which reuses `pendingSeek` + `playCurrent()` — the same mechanism session restore uses.
- Session keys (`musiklib:session`, `volume`, `muted`, `shuffle`) are **shared with `index.html` and must keep the same shape**; on one device the session continues between both views. `test_frontend.py::test_mobile_shares_the_session_with_the_desktop_page` guards that.
- Tracks without a `duration` get the queue's average length, otherwise the axis collapses.

**Frontend, the previous desktop surface (`index.html`)** is served at `/klassisch` since stage 4 and stays one release as the way back; it shares every storage key with the new page, so switching mid-song continues playback. It is one file with three parts in this order: `<style>` (CSS custom properties at the top of `:root` centralize theme — colors, fonts, `--player-h` — change those instead of scattering literal values), the DOM skeleton, then a single `<script>` with no modules/bundler. Key frontend concepts:
- `library` (fetched from `/api/library`) is the full in-memory dataset; `filtered` is the current search-filtered subset; both are plain arrays of album objects re-rendered on every filter/tab change (no virtual DOM/diffing).
- `queue` + `qIndex` model the play queue: clicking a track loads the whole album into `queue` starting at that index, so next/prev just moves `qIndex`.
- Playback state is driven off the single `<audio>` element's native events; there is no separate player state object. The play/pause button is updated **only** from the `play`/`pause` events via `setPlayButton()` — never set it optimistically next to an `audio.play()` call, or it desyncs the moment playback is controlled from outside the page (lockscreen, media keys, blocked autoplay). `playCurrent()` is the one place that changes what's playing; it also refreshes the Media Session metadata. `playNext()`/`playPrev()`/`togglePlay()` are shared by the player buttons and the Media Session action handlers, so lockscreen controls move the same queue.
- The `error` event on `<audio>` reports a track whose file moved since the last scan (the stream 404s). Without a handler the player just stops silently, so keep one.
- `groupByArtist()` derives the artist view from `library.albums` on the fly — there is no separate artists endpoint or artist data structure server-side.
- Search matches against `a._q`, a lowercase blob of album title, album artist and every track title/artist built once per load by `indexLibrary()`. Rebuild it whenever `library` is replaced; matching per keystroke is then a single `includes()` per album. `applyFilter()` also sorts, always into a **new** array — `library.albums` itself must stay in backend order.
- `SORTERS` holds the sort modes offered in the header; the chosen one is persisted under `musiklib:sort`. "Zuletzt hinzugefügt" reads `album.added_at`, which the backend derives from file mtimes.
- `loadQueue()` is the only place a queue is established — it applies shuffle by keeping the chosen track first and shuffling the rest. `playFromAlbum()` and `playArtist()` both go through it.
- Session continuity lives in `localStorage` under `musiklib:*` (`session`, `volume`, `muted`, `shuffle`, `sort`). `restoreSession()` rebuilds the queue from stored `[albumId, trackId]` pairs and silently drops entries that no longer resolve — which is what happens after files move, since `track_id` is path-derived. It never autoplays. All storage access goes through `store()`/`restore()`, which swallow failures: a browser with storage disabled must still run the app.
- `.album` carries `content-visibility: auto` with `contain-intrinsic-size`. If you change the card layout, update that size hint too, or scrolling a large library will jump.
- `pollScan()` re-polls `/api/scan/status` every 600ms while a scan runs and calls `loadLibrary()` once it finishes; this is the only path that refreshes the library after startup.
- The page loads IBM Plex Mono from Google Fonts (`<link>` in `<head>`). A NAS without internet access falls back to the system monospace — the layout survives, but don't assume the webfont is present.

**Frontend, third surface (`player.html`)** is served at both `/ipad` and `/pc`. What is unusual about it is that it does not have one appearance but **twelve**, all in the one file, freely switchable at runtime. Since stage 1 of the consolidation it is no longer a *pure* player: sorting, the artist view, triggering a scan and the skipped-files list moved in from `index.html`, so `/pc` can do everything `/` can. They all live in the settings dialog, the one surface all twelve layouts share — **no layout knows about any of it**.
- **A layout is a self-contained module**, registered with `layout({id, name, geraet, ziele, familie, klasse, chrome, text, bau(wurzel, deck)})`. `bau()` writes the markup, binds the controls and sets `deck.onRender`. Everything else — queue, audio, session, search, library mechanics — lives once in the substrate above the registry. Adding a thirteenth layout is one CSS block plus one `layout({…})` call and touches nothing else.
- **Every rule in the stylesheet belongs to exactly one root class** (`.dp`, `.sk`, `.ks`, `.wr`, `.rk`, `.sg`, `.nc`, plus modifiers like `.dp.voll`). Twelve appearances share one document; an unscoped selector colours the other eleven. Variants of one sheet differ only in their custom properties, set on the modifier class. `.bgruppe` is the **one deliberate exception** — see the artist view below.
- **`zeigeLayout()` is the only place a layout is built or torn down.** It clears `deck.onRender`, empties `#buehne`, resets `offeneBlenden` **and `listenZeichner`**, rebuilds and stores the choice under `musiklib:layout`. The `<audio>` element deliberately lives *outside* `#buehne` — that is why playback survives a layout change.
- **Sorting sits in `suche()`, not in the layouts.** All three list renderers on the page go through that one function (`bindBibliothek()` for ten layouts, `zeichneRegal()` for the `ks` family, `zeichneTextliste()` for "Werkstisch"), so the choice applies everywhere at once. `SORTIERUNGEN` carries the same five ids and the same meaning as `index.html`'s `SORTERS` under the same key `musiklib:sort` — only the field names are this page's short ones (`a.ar`, not `a.artist`). `suche()` sorts **into a new array**: `ALBUMS` itself must keep its order, because `naechstesAlbum()` and the first start index into it.
- **The artist view groups the layout's own rows, it doesn't replace them.** `listeHTML(alben, zeile, leer)` takes the row renderer the layout supplies and, when `ansicht === 'interpreten'`, inserts a `.bgruppe` heading before each artist's block. That is why `.bgruppe` is the only rule outside a root class — and why it must never name a colour: everything comes through `currentColor` from its surroundings, so it belongs on walnut as well as on frosted glass. It carries `grid-column:1/-1` because several lists are two-column grids (`.nc .bliste`, `.wr .spalten`); in flex and block contexts that is inert. `interpreten()` derives the grouping from the *filtered* album list, exactly as `index.html` does — there is no artist endpoint and there should not be one.
- **"Alles" on a group plays what is on screen**, not the artist's whole output: `bindeGruppen()` gets the same filtered list the headings were computed from, so with a search in the field the button matches what stands next to it. It is the one case where a queue is more than one album, which is why `Deck.ladeIds()` exists and `ladeAlbum()` is now just its common special case.
- **A scan is only ever started by the button.** On load the page just *asks* `/api/scan/status` once and picks up a scan that is already running (the container's first-start scan, for instance); it never triggers one. A player that spins up the NAS disk merely because a page opened would be a bug — `test_player_never_scans_just_because_the_page_opened` guards it. After a scan `nachScan()` re-takes the collection, drops queue entries whose files are gone and **does not touch the audio element**: whoever is listening should not notice a scan.
- **`listenZeichner` is how a setting reaches every open list.** Each renderer registers itself via `merkeListe()` while its layout is built; `zeichneListen()` redraws them all. Same lifecycle as `offeneBlenden`, cleared in the same place.
- **The `Deck` reads its state from the `<audio>` element, never from an assumption** (`playing` is `!audio.paused`, `pos` is `audio.currentTime`). Same rule as `index.html`'s play button, for the same reason: lockscreen, media keys and blocked autoplay all move the element without going through the UI.
- **`setzePos()` exists because the sheets seek on every pointer move.** It parks the target in `_ziel`, applies it once per animation frame and keeps returning it from `pos` until the element reports `seeked` (at most a second). Without it, dragging a tonearm would fire a seek storm and the handle would snap back on every `timeupdate`.
- **The API's flat albums are translated once into the drafts' shape** (`uebernimm()` → `a.t/.ar/.y/.tr[][]`, `TRACKS[id] = {t, d, al, no}`). Do that translation once and never in a layout: a layout that reaches into `library.json` directly re-opens the boundary the other two surfaces keep.
- **Fixed device sizes from the drafts are gone.** Anything large is a `min()`/`clamp()` over viewport units, so the same layout stands on an iPad in either orientation and in a desktop window. When porting a further sheet, replace its `--td: 420px` with a `min()` — don't scale the whole layout with `transform`.
- **Library and search are behind one button in every layout**, as a blind over the device, never as a separate page. Two exceptions are deliberate and tested: "Werkstisch" and "Deck" show the collection permanently, so their search line sits directly above the list (`test_player_library_and_search_are_reachable_in_every_layout` knows both names).
- Session keys are the ones the other two surfaces use (`musiklib:session`, `volume`, `muted`, `shuffle`, `fortsetzung`) in **exactly the same shape**, and `musiklib:sort` now joins them — set it here and the desktop page opens sorted the same way (`test_player_sorting_reorders_and_is_shared_with_the_desktop` guards both directions of that promise). `musiklib:layout`, `musiklib:ziel`, `musiklib:alleansichten`, `musiklib:ansicht` and `musiklib:wach` are this page's own and are ignored elsewhere.
- **`ziele` is the switch, `geraet` is only prose.** Every layout names the formats it was drawn for (`telefon` | `tablet` | `pc`), and the chooser shows only those. The values are measured, not guessed: each layout was checked on phone portrait, tablet portrait, tablet landscape and desktop for anything sticking out of the stage and for the play and library buttons being fully in view (`scratchpad`-style harness, re-runnable). Two calls came from looking rather than measuring, because nothing overflowed and it still did not work: **"Werkstisch" loses the track titles from its list on a phone** (only number and duration survive the column squeeze) and **"Register" pushes the record's centre off-screen in portrait**. Both are excluded there.
- **Filtering is a recommendation, not a fence.** `alleZeigen` (`musiklib:alleansichten`, a checkbox in the dialog) puts every layout back in the list. Nobody gets locked out of a look they like — they just get told it was not drawn for this format.
- **The layout choice is remembered per target**, all under the one key `musiklib:layout`, which is now an object (`{pc: 'werkstisch', tablet: 'konsole'}`). Same reasoning as `mobile.html`'s single settings object: later additions need no new key. A value from before stage 2 is a *string*; `gemerktesLayout()` accepts it for every target until the first write, so an existing choice survives the update (`test_player_carries_over_the_old_single_layout_key`). Without per-target memory, switching the look at the desk would change it on the iPad — same file, same storage.
- **The address is a preselection, not a device sniff.** `erkanntesZiel()` reads `/mobil` → telefon, `/ipad` → tablet, `/pc` → pc, and only a viewport whose shorter side is under 500px overrides that: a phone stays a phone whatever address you type. After that the choice in the dialog is the only thing that decides.
- **Every layout marks its seek surface with `data-spulen`.** Seven families seek on seven very different things — tonearm, groove, tape rail, hairline, metal wheel — and `test_player_every_layout_offers_transport_seeking_and_settings` should not have to know all of them. It asks for the marker, for `[data-pp]`/`[data-prev]`/`[data-next]`, and that the Wechsler is not covered (via `elementFromPoint`). That test is what found `.nc .band`'s `flex:1` in a *column* container, which set the height basis to 0 and left "Turm" with an unusable seek rail.
- **The five phone layouts are a port of `mobile.html`, not a rewrite.** "Papier"/"Desert Rose" are one family with two axes (`.pa` / `.pa.wu`), "Kissen" (`.mg`), "Karte" (`.aa`) and "Kiesel" (`.kl`) are one each. The translation is mechanical and documented in the file: `togglePlay`→`deck.toggle()`, `springeAufIndex(k)`→`deck.jump(k)`, `spuleImTitel(f)`→`deck.seek(f)`, `queue[i].track`→`TRACKS[deck.queue[i]]`, `offsets()/gesamt()/globalPos()`→`deck.offs/.total/.gpos`. Keep it that way — the sheet's vocabulary is what makes a later sheet cheap to bring over.
- **What the phone layouts deliberately drop is the tab bar.** In `mobile.html` collection and search are *pages*; here they are the blind every layout has, so the phone sheets' two head buttons both open it — left without focusing the field, right with (`bindBibliothek`'s `suchknopf`). On a phone, browsing must not raise the keyboard.
- **`bindAchse()` is not `bindDrag()`.** The queue axis spans the whole queue, so applying on every pointer move would load a new source per pixel once the drag crosses a track boundary. It parks the target in `deck._gziel` (which `gpos` returns while set) and applies once on release. The rail also keeps `mobile.html`'s 8px threshold: below it a tap unfolds the queue instead of seeking, because a tap that also seeks moves playback when the user only wanted to look. The horizontal scale has no threshold — there a tap is unambiguously a seek.
- **Accents belong to the layout, not to the page.** `layout({akzente:[{id,name,farbe}]})`, one `ak-<id>` CSS block per accent that redefines only the four accent properties. Ids are unique across all layouts, so one key `musiklib:akzent` suffices; `akzentFuer()` falls back to the layout's first when the stored one does not belong to it. Brass on sand would not be a choice but a mistake. "Karte" has exactly one accent on purpose and therefore offers no chooser.
- **The old phone settings are taken over once.** `musiklib:einstellungen` (`{thema, akzent, …}` from `mobile.html`) is read at start: the theme id *is* the layout id, so the carry-over is an assignment, not a conversion (`test_phone_takes_over_the_old_mobile_settings`).
- **Volume and mute live in the dialog, not only in the layouts.** Only seven of the seventeen carry a knob, arrow keys are no answer on a tablet, and "mute" had no place at all before. The slider hangs off `ton.volume`, the button off `ton.muted` — separate, so lifting the mute finds the old level again. `feldLaut.oninput` redraws only its own readout: letting `setVol()` refresh the whole dialog would rebuild the layout grid on every drag frame.
- **`familie` is set on every layout but nothing renders it yet.** Grouping twelve entries into seven families would add more chrome than clarity; the field is there so that the grouping is only a rendering job once the design package's sheets arrive. The filter line above the grid appears when a target offers more than `SICHTGRENZE` (12) layouts, for the same reason.

**Frontend, fourth surface (`tag.html`)** is served at `/tag` and is the smallest of the four: **one button and no choices**. It plays the *album of the day* — drawn from the collection, the same album all day, a different one tomorrow. Built from `mockups/player/14-album-des-tages.html` (variant 1) against `mockups/player/14-auftrag.md`; both explain the reasons behind what follows.
- **The one button is a plain toggle, applied immediately.** "Press once = play, twice = stop, again = resume" is literally a toggle. A *detected* double tap would mean waiting ~250 ms before every play — so the five-tap gesture is **counted alongside** instead: every tap toggles at once, and the fifth tap within `FENSTER` overrides the result (new album, playing). Don't turn this into a gesture recogniser.
- **`tippe()` redraws right after `deck.toggle()`.** That is not the optimistic button update `index.html` forbids: `zeichne()` reads `ton.paused`, which has already flipped. Without it the button lags until the `play` event, which a test caught.
- **The album of the day is computed, not rolled**: `hash(iso + '#' + schub) % ALBUMS.length` (FNV-1a) over the *local* date, so two devices with the same collection agree without ever talking. `albumDesTages()` also skips the album currently showing, so the same album never lands two days running. `ALBUMS` must therefore stay in a stable sort order — the choice is an index into that list.
- **`musiklib:tag`** (`{datum, albumId, schub, gewechselt}`) is this page's own key. The stored `albumId` **wins** while it still resolves: otherwise a scan mid-day would swap the album underfoot, just because the list length changed. `schub` counts up rather than re-rolling, so the second album of a day is reproducible too; `gewechselt` is what makes the five-tap gesture a once-a-day affair.
- **The day is checked, never scheduled**: on `visibilitychange`, at every track end and on a 60 s interval — a timer to midnight is exactly what iOS does not fire in the background. If audio is playing when the day turns, `tagWartet` defers the swap to the end of the running track.
- **The queue is one album and never ends** — after the last track it starts over. This page therefore neither reads nor writes `musiklib:fortsetzung` (its continuation is the day) and does not read `shuffle`. `session`, `volume`, `muted` keep the shared shape; `sitzungHolen()` accepts a session **only if every item belongs to the day's album**, so a session from another surface can't make the page play something other than what it displays.
- **`heute` and `FENSTER` are `let` at the top level** for the same reason `HEIL_VERZUG` is: otherwise the day change is only testable by waiting for a real night.
- **The progress ring states its own size** (`width`/`height`/`left`/`top`, not `inset`). `<svg class="ring">` carries no `width`/`height` attribute, so it is a replaced element with `width:auto`: Blink stretches such an element across all four given edges, WebKit takes 100% of the button instead and then shifts it by the negative `left`/`top` — on the iPhone the ring sat beside the disc rather than around it. Any absolutely positioned inline SVG on these pages needs its size written out for the same reason.
- **Both rows of `.karte` carry `min-width:0`** — the same rule `mobile.html`'s grid cards need, for the same reason. A grid item is by default at least as wide as its longest unbreakable content, and the footer's track line runs `white-space:nowrap`; a long title made the single column wider than the screen, which cut the footer off at the edge without an ellipsis and centred the disc in that too-wide column instead of on the screen. Guarded by `test_day_disc_stays_centred_under_a_long_track_title`. (The mockup sheet doesn't share this: there the disc and the footer are absolutely positioned.)
- **No cover, no `/api/cover`, no second button** — not even a hidden one. Media Session gets `play`/`pause` handlers only, and `musiklib:wach` is *read* here but has no control of its own; it is set on `/mobil` or `/ipad`.

**Playback keeps going — the three failure modes, handled identically in all four surfaces.** These were found on a real iPhone against a real NAS; the code exists because the platform makes each of them silent.
- **A refused track change is the common one.** At the end of a track the element gets a new `src`, and iOS in the background treats that as a *new* start rather than a continuation and rejects `play()` — which used to disappear into `.catch(() => {})`. `nachdruck()` re-asks every `NACH_VERZUG` ms up to `NACH_MAX` times, and again on `visibilitychange` when the page returns to the foreground. **`tonGewuenscht` is what separates a refused start from a deliberate pause** — set true wherever playback is requested, false in the user's own pause paths (toggle, Media Session pause, end of queue). Without it the retry loop would fight the pause button and resume during a phone call.
- **A stalled stream** (throttled Wi-Fi, sleeping NAS disk) fires `waiting`/`stalled` and then nothing ever again. `heilungPlanen()` arms a timer that reloads the same source at the same position (via the existing `pendingSeek`/`_pending` mechanism); every `timeupdate` cancels it again, because progress means health. `error` only retries for `MediaError` codes 2/3 (network, decode) — code 4 is a file that moved since the last scan, and no number of retries will bring it back, so that one still reports.
- **The end of the queue.** A queue is one album. `musiklib:fortsetzung` (`weiter` | `wiederholen` | `halt`, default `weiter`) is a **shared key like `volume` and `shuffle`** and decides what happens next; `weiter` loads the next album in collection order. Each surface renders its own control (settings group on the phone, a section in the layout sheet in the player, a cycling button next to shuffle on the desktop) but they all write the same key. `tag.html` is the deliberate exception: it neither reads nor writes the key, because its queue repeats until the day ends.
- `ladeVor()` fetches the first 256 KB of the *next* track 25 s before the end and throws the body away. That warms the connection and spins the NAS disk up before it is needed; the element's own `preload` is useless here because iOS ignores it.
- **`musiklib:wach`** (set on the phone and in the player, read by `tag.html` too) holds a screen wake lock while audio is playing, which is what actually prevents iOS from throttling Wi-Fi. It is off by default because a lit screen costs battery, the lock is released by iOS whenever the page is hidden, and it must therefore be re-requested on `visibilitychange`.
- `HEIL_VERZUG` and `NACH_VERZUG` are `let`, not `const`, so the frontend tests can shorten them instead of waiting seconds.

**Data flow contract**: the backend never mutates `library.json` structure per-request and the frontend never talks to the filesystem — all album/track shape decisions belong in `scan()`/`read_tags()`, and all display/filtering logic belongs in `index.html`. Keep that boundary when adding fields (e.g., a new ID3 tag needs to flow through `read_tags` → `scan` → `library.json` → frontend render code, in that order).

## Conventions worth preserving

- No database, no ORM — flat JSON files by design (see README "Was die App nicht macht"). Don't introduce one for small features.
- No build tooling for the frontend — keep `index.html`, `mobile.html` and `player.html` single static files editable via SMB and reloadable without a container restart (per README, this is a deployment requirement, not just a style choice). This is also why `player.html` carries twelve layouts instead of twelve files: one file to copy, one file to edit.
- Deployment installs dependencies at container start (`pip install -r requirements.txt` in the compose `command`, no image build), so adding a dependency requires a full container stop/start, not a restart. Keep `requirements.txt` small and pinned.
- Cover filenames are content-addressed (`{album_id}.{ext}`) and validated against path traversal in `/api/cover/{name}` (rejects `/`, `\`, `..`) — preserve that check if touching that endpoint.
- User-facing strings in all three frontends are German; the backend's tag fallbacks (`"Unbekanntes Album"`, `"Unbekannter Interpret"`) are too. Match that when adding UI text.
- `README.md` is in German and documents unraid-specific deployment/troubleshooting in detail; consult it before changing deployment-relevant behavior (env vars, ports, volume expectations).
